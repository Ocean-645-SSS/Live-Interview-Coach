# Job Facts to Job Profile Implementation Plan

**Goal:** Make Job-side preparation symmetric with Candidate-side preparation: a bounded LLM extracts grounded `JobFacts`; deterministic application code converts those facts into `JobProfile`; the planner consumes only the profile's taxonomy-key weights.

## Code-fact audit

- `liverag/interview/application/resume_parser.py::ResumeParser.parse` retrieves candidate context, invokes one structured LLM extraction, validates `CandidateFacts`, and retries once after invalid output.
- `liverag/interview/application/profile_service.py::InterviewProfileService.build_candidate_profile` consumes `CandidateFacts` and applies deterministic rules (`skills`, `_infer_experience_level`, `_project_lines`) to build `CandidateProfile`.
- `liverag/interview/jobs/tasks.py::resume_parse_task` persists standalone CandidateFacts in the existing `BackgroundJob.result_json`; `_generate_candidate_profile` reloads it through `candidate_facts_job_id`. During `interview_preparation_task`, CandidateFacts are transient stage data and are regenerated after interrupted preparation.
- There is no `JobFacts` equivalent. `build_job_profile` retrieves JD context and creates a raw summary with empty `required_skills`.
- CandidateFacts itself has no database table. CandidateProfile is the only persisted Candidate snapshot (`candidate_profiles.latest_profile_json`), and each frozen `InterviewPlan` is saved in `interviews.plan_json`. JobFacts should use the same job-result/transient-stage lifecycle, so no new table or Alembic migration is warranted.

## Design decisions

- Add grounded Job facts needed for audit and deterministic profiling: raw JD text, job title, responsibility excerpts, required/preferred taxonomy-normalized skill facts, explicitly named framework/tool facts, experience requirements, education requirements, and evidence references.
- `JobFactsExtractor` is the Job-side analogue of `ResumeParser`: retrieval, structured JSON response, Pydantic validation, taxonomy/evidence validation, and one retry. If the LLM call or validation still fails, it uses a bounded rule/keyword fallback and marks the result `FALLBACK` with lower confidence. It never decides weights or creates questions.
- `InterviewProfileService.build_job_profile` accepts optional `JobFacts`. It makes the existing raw context summary deterministically and derives `JobSkill` weights as required `1.0` and preferred `0.6`. It performs no LLM call.
- The primary asynchronous preparation workflow gains an explicit `JOB_FACTS_EXTRACTION` stage before `JOB_PROFILE`. A standalone `job_parse` job and `job_facts_job_id` mirror `resume_parse` and `candidate_facts_job_id` for profile-only jobs.
- Existing synchronous `/prepared` behavior remains a raw-summary fallback when it has no JobFacts extractor stage, matching the Candidate-side direct profile fallback. The regular asynchronous preparation path receives the complete JobFacts → JobProfile path.
- The planner receives only `JobProfile` skills. QuestionBank adds the `2.0 * weight` ranking dimension based on a question's taxonomy key, and frozen plan questions carry matching `JobSkill` evidence plus the applied score.

## Implementation and verification

1. Extend schemas with `JobSkillFact`, `JobFacts`, `JobSkill`, required/preferred partition validation, and frozen-question JobSkill audit fields.
2. Implement `JobFactsExtractor` and its strict prompt. Tests cover known IDs, required/preferred distinction, exact evidence, invalid IDs, retry, and LLM failure.
3. Update ProfileService and job handlers/workflow to load JobFacts before deterministic profile generation. Reduce the deterministic JobProfile skill weights when facts were generated by the bounded fallback; do not make fallback facts a hard failure.
4. Update curriculum, QuestionBank, Planner, and the personalization prompt so taxonomy-key JobProfile weights influence ranking without replacing candidate, company, SkillProgress, difficulty, count, or duration constraints.
5. Test the full set in `tests/interview/test_job_profile_extractor.py` and compatible existing background-job tests; run Ruff for all touched files.
