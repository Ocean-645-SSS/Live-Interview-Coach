# LiveRAG 第一版测试发现

## 当前状态

项目目前已经验证：

* Docker Compose 能够启动前端、API、RAG、LiveKit 和 Agent；
* 前端页面可以访问；
* 文档可以上传并建立索引；
* 麦克风语音可以完成 STT 转写；
* Agent 可以调用知识库并生成回答；
* TTS 能够正常播放回答；
* LiveKit 实时通话链路已经跑通。

以下问题暂时统一标记为 `Deferred`，待第一版复现完成后处理。

## ISSUE-001：索引过程中无法取消或删除文档

* 类型：任务控制/交互缺陷
* 优先级：P1
* 现象：文档上传并进入索引阶段后，如果用户想放弃，只能等待索引结束，不能取消任务，也不能直接删除文件。
* 风险：耗时任务和 Embedding API 调用无法及时终止。
* 后续目标：增加取消索引能力，安全停止后台任务，清理已经产生的临时分块和向量，再允许删除文档。

## ISSUE-002：无法切换助手音色

* 类型：功能缺失
* 优先级：P2
* 现象：助手音色由后端或环境变量固定，前端没有音色选择和试听入口。
* 后续目标：允许用户在通话开始前选择 TTS 音色，第一版可以限定为下一场通话生效。

## ISSUE-003：索引过程缺少进度反馈

* 类型：用户体验优化
* 优先级：P2
* 现象：文档建立索引时只有等待状态，用户不知道当前处于解析、分块、Embedding 还是写入阶段，也不知道还需要等待多久。
* 后续目标：优先显示真实阶段；如果后端能够提供处理数量，再显示真实的 0%～100% 进度。禁止仅由前端模拟虚假百分比。

## ISSUE-004：知识库检索响应过慢

* 类型：RAG 性能/Agent 工具调用问题
* 优先级：P1
* 复现场景：文档中写入“Susie 项目的内部代号是 Blue Cactus 731，计划于 2031 年 9 月交付”，然后在语音对话中询问对应问题。
* 现象：等待大约半分钟仍没有直接给出答案，用户再次追问后，助手才表示已经找到结果。
* 后续排查：分别记录查询改写、Embedding、向量检索、RAG API、LLM 首 Token、工具调用和 TTS 的耗时，确认是否存在超时、重试或工具调用结果未及时进入当前回答的问题。
* 后续目标：正常规模知识库中的特殊事实查询应在合理时间内返回，并提供清晰的“正在检索”状态。

## ISSUE-005：刷新页面后历史对话文字消失

* 类型：会话恢复/状态持久化问题
* 优先级：P1
* 现象：通话过程中刷新浏览器页面，已经显示的用户和 AI 对话文字全部消失。
* 备注：目前尚未确认是后端没有保存会话，还是前端刷新后没有重新获取会话记录。
* 后续目标：刷新后能够根据 session/room 标识恢复当前会话的历史记录；如果产品明确不支持恢复，也应该在刷新前给予提示。

## ISSUE-006：长回答遮挡底部工具栏

* 类型：严重 UI 交互问题
* 优先级：P0
* 现象：AI 单次回答文字较长时，对话内容会覆盖或挤压页面底部工具栏，导致用户无法点击“结束通话”。
* 后续目标：对话区域独立滚动，工具栏固定且始终可见；长文本、不同分辨率和浏览器缩放下都不能遮挡挂断按钮。

## ISSUE-007：上传文档不显示原始文件名

* 类型：文件元数据/展示问题
* 优先级：P1
* 现象：上传后的文档名称变成随机生成的名称，用户无法确认它对应哪个原始文件。
* 后续目标：后端可以继续使用 UUID 或随机名称保存物理文件以避免冲突，但必须单独保存 `original_filename`，前端默认展示原文件名。

## ISSUE-008：无知识库证据时产生幻觉

* 类型：RAG 正确性/知识库隔离问题
* 优先级：P0
* 复现场景：询问另一个知识库中不存在的特殊信息，例如项目内部代号。该知识库的文档没有提供内部代号，但助手回答内部代号是“Echo”。
* 现象：系统在无检索证据的情况下生成了看似确定的答案。
* 可能方向：

  1. 会话绑定了错误的知识库；
  2. 不同知识库之间发生数据或缓存串扰；
  3. 检索没有命中，但 LLM 仍根据自身知识或上下文猜测；
  4. 上一轮知识库内容残留在会话上下文中。
* 后续目标：

  * 每次检索必须明确记录实际使用的 `kb_id`；
  * 不同知识库的数据、缓存和会话上下文必须隔离；
  * 没有有效 evidence 时，助手必须明确说明当前知识库未提供相关信息；
  * 不得把模型猜测描述成知识库事实；
  * 调试信息应能查看检索命中、来源文档和证据片段。

## ISSUE-009：用户尚未说完时系统提前结束当前语音轮次

* 类型：实时语音端点检测/对话轮次控制问题
* 优先级：P0
* 状态：Deferred

### 问题现象

用户正在说一个较长的问题时，只要中途出现短暂停顿，系统就会提前认为用户已经说完：

1. 当前语音片段被过早提交为最终转写；
2. Agent 在上下文不完整时开始调用 RAG 或 LLM；
3. 用户后半句话被识别成新的对话轮次；
4. 页面中的用户发言和助手回答呈现断断续续的状态；
5. 助手没有听完完整问题便开始回答，容易出现答非所问、检索关键词不完整或错误回答。

例如，用户原本想连续表达：

“请根据知识库介绍 Susie 最近正在做的项目，以及这个项目涉及了哪些技术。”

如果用户在“正在做的项目”后短暂停顿，系统可能立即提交前半句话并开始回答，后面的“涉及了哪些技术”又被当成下一轮输入。

### 问题定义

需要区分以下两个概念：

* 实时临时转写：用户说话过程中持续显示识别文字，这是正常行为；
* 最终提交并触发回答：只有确认用户完成当前发言后，才能将文本作为完整用户轮次交给 Agent。

当前问题主要是第二项触发过早，而不一定是 STT 本身识别错误。

### 后续排查方向

后续修复阶段需要检查：

1. LiveKit Agent 的 VAD 配置；
2. 最短静音判定时间；
3. endpointing delay 或 end-of-turn delay；
4. STT interim transcript 与 final transcript 的处理逻辑；
5. Agent 是否在收到临时转写时就错误触发了回答；
6. 是否启用了语义轮次检测模型；
7. 用户继续说话时，能否取消尚未正式输出的回答；
8. 中文自然停顿、语气词和长句对端点检测的影响。

### 预期行为

* 用户说话过程中的临时转写可以实时显示；
* 短暂停顿不能立即触发 Agent 回答；
* 系统应等待合理的静音时间或结合语义判断用户是否说完；
* 最终提交给 RAG/LLM 的内容应尽量是一轮完整问题；
* 用户继续说话时，不应把同一句话拆成多个无关轮次；
* 如果助手刚准备回答但检测到用户继续发言，应支持取消或延迟当前回答。

### 后续验收场景

使用以下测试句进行验证：

“请根据知识库告诉我，Susie 最近正在做什么项目……这个项目主要使用了哪些技术……以及计划什么时候交付？”

测试时在两个省略号位置分别自然停顿约 0.5～1.5 秒，并确认：

1. 页面可以显示实时临时转写；
2. 系统不会在短暂停顿后立即回答；
3. 整句话最终作为一个完整用户轮次提交；
4. Agent 根据完整问题进行一次检索和回答；
5. 不会产生多个碎片化的 `YOU` 消息。

## 后续处理顺序

第一阶段：完成原项目第一版复现、测试并提交 Git 基线版本。

第二阶段：优先处理 P0：

1. ISSUE-008 无证据时产生幻觉；
2. ISSUE-009 用户尚未说完时系统提前结束当前语音轮次；
3. ISSUE-006 长回答遮挡挂断按钮。

第三阶段：处理 P1：

1. ISSUE-004 RAG 检索延迟；
2. ISSUE-005 刷新后的会话恢复；
3. ISSUE-001 索引取消；
4. ISSUE-007 原文件名保存和显示。

第四阶段：处理 P2：

1. ISSUE-003 索引进度展示；
2. ISSUE-002 TTS 音色选择。
